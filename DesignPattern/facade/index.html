Facade Pattern

Provide a simple, unified interface that hides the complexity of a subsystem. The client asks for a high-level operation; the Facade coordinates the lower-level pieces.

← All patterns

1. Intuition — why do we need it?

Imagine a game client trying to make a move. Without a Facade, it may need to know the correct sequence: validate the move, update the board, check for a win, check for a draw, and switch the player. Every caller must understand that workflow.

Key idea: Facade does not necessarily replace subsystem classes. It gives clients a simpler front door and coordinates their use.

2. Problem vs solution

Without Facade

  • Client calls multiple subsystem objects directly.
  • Client must know call order and workflow details.
  • Changes in the workflow can affect many callers.

With Facade

  • Client calls one high-level method, e.g. makeMove().
  • Facade coordinates the subsystem internally.
  • Subsystem remains available for clients that need lower-level control.

4. C++ example — Tic-Tac-Toe move

class Game { // Facade / coordinator
    Board board;
    Player x{"X"}, o{"O"};
    Player* current = &x;
    GameState state = GameState::IN_PROGRESS;

public:
    bool makeMove(int r, int c) {
        if (state != GameState::IN_PROGRESS)
            return false;

        if (!board.placeMark(r, c, current->getMark()))
            return false;

        if (board.checkWin(r, c))
            state = GameState::WON;
        else if (board.isFull())
            state = GameState::DRAW;
        else
            current = (current == &x) ? &o : &x;

        return true;
    }
};

// Client usage:
game.makeMove(row, col);

Board, Player and GameState are supporting types; this snippet focuses on the Facade’s role and workflow.

5. Where is it useful?

  • Subsystem APIs: one entry point to coordinate several library components.
  • Application services: a high-level operation that orchestrates repositories, validators, and other services.
  • Complex initialization: hide the required setup sequence behind a simple method.
  • Legacy integration: provide a cleaner interface over a complicated or awkward subsystem.

6. Trade-offs

Benefits

  • Simplifies client usage.
  • Reduces coupling to subsystem details.
  • Centralizes a common workflow.

Watch out

  • Facade can become a “god class” if it accumulates unrelated logic.
  • It should coordinate, not absorb every subsystem responsibility.
  • Not every coordinator needs to be labeled a Facade in an interview.

7. Facade vs Adapter

Facade simplifies access to a subsystem by offering a convenient interface.

Adapter translates one interface into another so incompatible interfaces can work together.

8. Interview checklist

  1. Explain why the client currently knows too much about subsystem details.
  2. Identify the high-level operation clients actually need.
  3. Show how the Facade delegates and coordinates.
  4. Clarify that subsystem classes still own their own responsibilities.
  5. Mention the risk of turning the Facade into a god object.

One-line definition: Facade provides a unified, higher-level interface to make a complex subsystem easier to use.
