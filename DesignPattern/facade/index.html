Facade
Pattern

Provide a simple, unified interface that hides the complexity of a subsystem. The client asks for a high-level operation; the Facade coordinates the lower-level pieces.

Our story: A game client wants to make a move. Why should it need to know the whole workflow behind that one move?

01INTUITION

Why do we need it?

First validate, then update the board, check win, check draw, switch player…

Without a Facade, every caller must understand the correct sequence of the workflow.

Make a move!

→

I coordinate it.

→

Board, player, state.

Facade does not necessarily replace subsystem classes. It gives clients a simpler front door and coordinates their use.

02PROBLEM VS SOLUTION

One front door

WITHOUT FACADE
validate→place mark→check win→check draw→switch player
  • Client calls multiple subsystem objects directly.
  • Client must know call order and workflow details.
  • Changes in the workflow can affect many callers.
WITH FACADE
makeMove(r, c)
  • Client calls one high-level method, e.g. makeMove().
  • Facade coordinates the subsystem internally.
  • Subsystem remains available for clients that need lower-level control.

Details

Facade usually has associations/dependencies to subsystem classes; it does not need to inherit from them.

04C++ EXAMPLE

Tic-Tac-Toe move

class Game { // Facade / coordinator
    Board board;
    Player x{"X"}, o{"O"};
    Player* current = &x;
    GameState state = GameState::IN_PROGRESS;

public:
    bool makeMove(int r, int c) {
        if (state != GameState::IN_PROGRESS)
            return false;

        if (!board.placeMark(r, c, current->getMark()))
            return false;

        if (board.checkWin(r, c))
            state = GameState::WON;
        else if (board.isFull())
            state = GameState::DRAW;
        else
            current = (current == &x) ? &o : &x;

        return true;
    }
};

// Client usage:
game.makeMove(row, col);
Supporting types (declarations only) 
enum class GameState { IN_PROGRESS, WON, DRAW };

struct Player {
    explicit Player(std::string mark);
    const std::string& getMark() const;
};

class Board {
public:
    bool placeMark(int r, int c, const std::string& mark);
    bool checkWin(int r, int c) const;
    bool isFull() const;
};

Board, Player and GameState are supporting types; the snippet above focuses on the Facade's role and workflow.

05USE CASES

Where is it useful?

Subsystem APIs

One entry point to coordinate several library components.

Application services

A high-level operation that orchestrates repositories, validators, and other services.

Complex initialization

Hide the required setup sequence behind a simple method.

Legacy integration

Provide a cleaner interface over a complicated or awkward subsystem.

06TRADE-OFFS

Benefits and watch-outs

Coordinate, don't absorb!

  • Simplifies client usage.
  • Reduces coupling to subsystem details.
  • Centralizes a common workflow.
  • Facade can become a “god class” if it accumulates unrelated logic.
  • It should coordinate, not absorb every subsystem responsibility.
  • Not every coordinator needs to be labeled a Facade in an interview.
07COMPARE

Facade vs Adapter

I simplify access to a subsystem.

I translate one interface into another.

Facade offers a convenient interface to a subsystem. Adapter translates one interface into another so incompatible interfaces can work together.

08INTERVIEW

Checklist

  • Explain why the client currently knows too much about subsystem details.
  • Identify the high-level operation clients actually need.
  • Show how the Facade delegates and coordinates.
  • Clarify that subsystem classes still own their own responsibilities.
  • Mention the risk of turning the Facade into a god object.

One-line definition: Facade provides a unified, higher-level interface to make a complex subsystem easier to use.

CHECKPOINT

Can you explain Facade without notes?

Try answering aloud before revealing the short answer.

Why use a Facade?

Clients shouldn't need to know the subsystem's call order. The Facade exposes one high-level operation and coordinates the pieces behind it.

Does a Facade replace the subsystem classes?

No. It is a simpler front door; the subsystem remains available for clients that need lower-level control.

Facade vs Adapter?

Facade simplifies access to a subsystem. Adapter translates one interface into another so incompatible interfaces can work together.

What is the main risk?

It can become a god class if it accumulates unrelated logic. It should coordinate, not absorb the subsystem's responsibilities.

Must the Facade inherit from the subsystem classes?

No. It usually holds associations or dependencies to them and delegates the work.
