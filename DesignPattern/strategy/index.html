Strategy
Pattern

Define a family of algorithms, encapsulate each one, and make them interchangeable. The client uses a common interface while the chosen strategy decides how the work is done.

Our story: A checkout system supports card, UPI, and wallet payments. Should Checkout contain every payment algorithm?

01INTUITION

What varies?

Card payment, UPI payment, wallet payment… each has a different algorithm.

The checkout flow is stable, but the payment method changes. Put each algorithm behind the same interface and select the one needed.

Pay using this method.

→

I delegate to the chosen strategy.

→

I execute the algorithm.

Strategy is about encapsulating behavior that varies—not simply creating classes for every object.

02PROBLEM VS SOLUTION

Replace the growing if-else

WITHOUT STRATEGY
if (method == CARD)
    payByCard();
else if (method == UPI)
    payByUpi();
else if (method == WALLET)
    payByWallet();
  • Checkout knows every algorithm.
  • Adding a method changes existing code.
  • Branches and testing grow over time.
WITH STRATEGY
PaymentStrategy* strategy =
    choosePaymentMethod();

checkout.pay(*strategy);
  • Checkout depends on an interface.
  • Each algorithm lives in its own class.
  • New strategies can be added independently.

The if-else may still exist in a composition/root selection point. The goal is to keep algorithm branches out of the core workflow.

04C++ EXAMPLE

Payment strategies

#include <iostream>
#include <memory>
using namespace std;

class PaymentStrategy {
public:
    virtual bool pay(int amount) = 0;
    virtual ~PaymentStrategy() = default;
};

class CardPayment : public PaymentStrategy {
public:
    bool pay(int amount) override {
        cout << "Paid " << amount << " by card\n";
        return true;
    }
};

class UpiPayment : public PaymentStrategy {
public:
    bool pay(int amount) override {
        cout << "Paid " << amount << " by UPI\n";
        return true;
    }
};

class Checkout {
    PaymentStrategy& strategy;
public:
    explicit Checkout(PaymentStrategy& s) : strategy(s) {}
    bool pay(int amount) { return strategy.pay(amount); }
};

int main() {
    UpiPayment upi;
    Checkout checkout(upi);
    checkout.pay(500);
}

Swap UpiPayment for CardPayment without changing Checkout. In production, strategies can validate inputs, call gateways, and report failures.

05USE CASES

Where is it useful?

Payment methods

Card, UPI, wallet, or other interchangeable payment algorithms.

Pricing / discounts

Regular pricing, seasonal discounts, coupons, or loyalty rules.

Routing

Choose shortest-path, fastest, or toll-avoiding route algorithms.

Compression / sorting

Select an algorithm based on data, quality, or performance needs.

06TRADE-OFFS

Benefits and watch-outs

Encapsulate what varies!

  • Removes algorithm-specific branching from the context.
  • Algorithms can be tested independently.
  • New strategies are easier to add or swap at runtime.
  • Adds interface and concrete strategy classes.
  • Client/composition code must choose the right strategy.
  • Avoid it when there are no meaningful variations; simple code may be clearer.
07COMPARE

Strategy vs State

I choose an algorithm for a task.

I change behavior as the object's state changes.

Strategy: behavior is selected by the client/configuration; strategies are usually interchangeable alternatives. State: behavior changes as the context transitions between states, often with state objects controlling transitions.

Strategy vs Template Method: Strategy uses composition to swap a whole algorithm; Template Method uses inheritance to customize steps of a fixed algorithm skeleton.

08INTERVIEW

Checklist

  • Identify the algorithm or behavior that varies.
  • Define a common strategy interface.
  • Move each algorithm into a concrete strategy.
  • Make the context delegate rather than branch on concrete types.
  • Explain who selects the strategy and why the extra abstraction is worthwhile.

One-line definition: Strategy encapsulates interchangeable algorithms behind a common interface so they can vary independently from the client that uses them.

CHECKPOINT

Can you explain Strategy without notes?

Try answering aloud before revealing the short answer.

What problem does Strategy solve?

It isolates a family of algorithms that vary and lets the context use any one through a common interface, avoiding algorithm-specific branching in the workflow.

Why do we need the Context?

The Context represents the stable workflow (such as Checkout) and delegates the varying step to the injected strategy.

Who chooses the strategy?

Usually the client, configuration, or a composition layer chooses it and supplies it to the Context.

Strategy vs State?

Strategy selects interchangeable algorithms; State changes behavior in response to the context's internal state and transitions.

When should we avoid it?

When behavior does not meaningfully vary or the abstraction makes simple code harder to understand.
