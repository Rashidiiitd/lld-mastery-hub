FOUNDATION

Process vs Thread

One process = one running program container
Process its own address space
Shared resourcescode · globals · heap · open files
T1stack + registers
T2stack + registers
T3stack + registers

Process: “I own the resources and address space.”

Thread: “I share process resources, but I have my own stack and execution state.”

A process is a resource container. A thread is an execution path inside that process. Shared memory enables communication, but threads must coordinate access.

Threads share code, globals and heap; each thread has its own stack, registers and program counter.

EXECUTION

Concurrency vs Parallelism

Concurrency: “I take turns so both tasks progress.”

Parallelism: “We are literally running at the same time!”

Concurrency is about structuring multiple tasks in progress. Parallelism is simultaneous execution, usually on multiple cores.

Concurrency is coordination; parallelism is simultaneous execution.

C++ API

Create a thread

Main threadcreates worker
std::thread t(worker) →
Workerruns callable
#include <thread>
#include <iostream>

void worker() {
    std::cout << "Hello from worker\\n";
}
int main() {
    std::thread t(worker);
    t.join();
}

Constructing a std::thread starts execution. The callable may begin before the constructor returns, so don't assume timing without synchronization.

A std::thread must be joined or detached before its destructor runs.

LIFETIME

join() vs detach()

Main
Createjoin() · waitsContinue
Worker
Work…Finish
Main + detach
Createdetach()Continue now

join(): “I won't continue until you finish.”

detach(): “Keep running independently; I won't wait.”

  • join() blocks the calling thread until the worker completes.
  • detach() separates execution from the thread object.
  • After either operation, the thread object is no longer joinable.
Detach carefully: the worker must not outlive objects it references. Completion and cancellation become harder to manage.
Prefer join() or std::jthread for managed lifetimes.

Conceptually, a thread may be runnable, executing, waiting for I/O or a lock, or completed. The OS scheduler decides when runnable threads get CPU time.

A thread can be alive but not currently running — it may be ready or blocked.
07

HARDWARE

Cores & context switching

Core 1Thread A
Core 2Thread B
OS saves state
and restores another

CPU: “A core executes a hardware thread at a time.”

OS: “I switch which thread gets the core.”

A context switch saves execution state (registers, instruction pointer, etc.) and restores another thread's state. SMT exposes multiple logical CPUs per physical core; they are not equivalent to separate physical cores.

More threads do not automatically mean more speed. Context switching and contention have costs.

Scheduler: “I choose who runs based on policy, priority, and system conditions.”

Preemption means the OS can pause a running thread and schedule another. Application code should not rely on exact timing or output order without synchronization.

Thread scheduling is nondeterministic from the program's point of view.

User-level threads are managed by a runtime/library. Kernel threads are known to and scheduled by the OS. std::thread typically maps to an OS thread on mainstream platforms, but implementation details are platform-dependent.

Know the distinction; avoid claiming every C++ implementation uses the same mapping.

THREAD UTILITIES

sleep_for, yield, get_id

sleep_for()std::this_thread::sleep_for(200ms);

Pause this thread for at least a duration; it may resume later.

yield()std::this_thread::yield();

Hint that the scheduler may run another thread.

get_id()std::this_thread::get_id();

Get an identifier for the current thread.

Neither sleep_for() nor yield() is a synchronization primitive. Don't use timing to fix a race.

C++20

std::jthread

Scope begins
construct jthread →
Worker runs
Scope ends ↓
request stop + join
#include <thread>
void work() { /* do work */ }
int main() {
    std::jthread worker(work);
    // automatically joins at scope exit
}

std::jthread automatically joins on destruction. If the callable accepts a stop_token, destruction requests stop before joining.

jthread improves lifetime safety, but cancellation is cooperative.
12

C++20

stop_token & cooperative cancellation

Workerchecks stop request
request_stop() →
Controllerasks politely
#include <thread>
void work(std::stop_token stop) {
    while (!stop.stop_requested()) {
        // do a small unit of work
    }
}
int main() {
    std::jthread t(work);
    t.request_stop();
}

Controller: “Please stop at a safe point.”

Worker: “I’ll finish this step, check the token, and exit.”

A stop request does not forcibly terminate a thread. The worker must observe the token. If blocked indefinitely, design a wake-up mechanism too.

Cancellation is a protocol — not a kill switch.

CHAPTER CHECKPOINT

Can you explain these without notes?

Try answering aloud. Reveal the short answer after you attempt it.

Why does a thread have its own stack?

Each thread needs its own call frames and local execution state while sharing process-level resources like code and heap.

Does join() make the worker run faster?

No. It synchronizes completion by making the calling thread wait; it doesn't speed up the worker.

Why is detach() risky?

The detached worker may outlive referenced objects, and its completion/cancellation becomes harder to manage.

Does yield() guarantee another thread runs?

No. It's only a scheduling hint and has no synchronization guarantee.

Does request_stop() immediately terminate a jthread?

No. It requests cooperative cancellation; the worker must observe the stop token and respond.
