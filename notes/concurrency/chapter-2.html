01INTUITION

What is a race condition?

I read count = 10

I also read count = 10

count = 10

A computes 10 + 1 → 11

B computes 10 + 1 → 11

Both write 11 → expected 12, got 11!

A race condition happens when the result depends on the unpredictable timing/order of threads accessing shared state.

Why did this happen?

count++ is not one indivisible action. It usually means load the value, add one, then store it. The threads can interleave those steps.

02CRITICAL SECTION

Find the dangerous region

Only one thread at a time, please!

++count; // read-modify-write
// critical section: touches shared state

A critical section is code that accesses shared data and must obey a coordination rule.

Enter→Critical section→Exit

The goal is not “make everything single-threaded”; it is protect only the operations that need protection.

03MUTEX

Mutual exclusion with std::mutex

I own the lock now.

I'll wait until it's free.

#include <mutex>
std::mutex m;
int count = 0;

void increment() {
    m.lock();
    ++count;
    m.unlock();
}

Only one thread can own a mutex at a time. Other threads trying to lock it wait.

Manual unlock is fragile: an early return or exception can leave the mutex locked.

04RAII

std::lock_guard — lock and unlock automatically

Constructor locks. Destructor unlocks.

std::mutex m;
int count = 0;

void increment() {
    std::lock_guard<std::mutex> lock(m);
    ++count;
} // lock releases here

lock_guard uses RAII: the lock's lifetime follows the object's scope, even if the function returns early or throws.

Default choice for a simple “lock this mutex for this scope” situation.

05FLEXIBLE LOCKING

std::unique_lock

I can lock now, later, unlock, and relock.

std::unique_lock<std::mutex> lock(m, std::defer_lock);
// do work that doesn't need the lock
lock.lock();
update_shared_state();
lock.unlock();
// more independent work

unique_lock is more flexible than lock_guard. It can be deferred, manually unlocked/relocked, moved, and used with condition variables.

Use it when you need those features; otherwise lock_guard is simpler.

06MULTIPLE LOCKS

std::scoped_lock — lock more than one mutex safely

A locks X, then waits for Y.

B locks Y, then waits for X.

Deadlock: each thread holds one lock and waits forever for the other.

std::mutex x, y;

void transfer() {
    std::scoped_lock lock(x, y);
    // safely use both protected resources
}

scoped_lock (C++17) acquires multiple mutexes using a deadlock-avoidance algorithm and releases them at scope exit.

When you need multiple mutexes together, prefer scoped_lock over hand-written lock ordering.

07READERS & WRITERS

std::shared_mutex and std::shared_lock

Many readers can enter together.

A writer needs exclusive access.

#include <shared_mutex>
std::shared_mutex m;
int value = 0;

int read() {
    std::shared_lock lock(m); // shared/read lock
    return value;
}
void write(int v) {
    std::unique_lock lock(m); // exclusive/write lock
    value = v;
}

Multiple shared locks can coexist. A unique lock excludes readers and other writers. Use when reads are frequent and writes are less frequent.

It may not improve performance for tiny/contended data; fairness/starvation behavior depends on implementation.

08SPECIAL CASE

std::recursive_mutex

Same thread can lock me repeatedly.

std::recursive_mutex m;
void outer() {
    std::lock_guard lock(m);
    inner(); // inner locks m again
}
void inner() {
    std::lock_guard lock(m);
    // ...
}

Useful when a locked function calls another function that also locks the same mutex, in the same thread.

Often hides unclear lock ownership or tangled call paths. Prefer redesigning private “already locked” helpers when practical.

09TRY / TIMEOUT

std::timed_mutex and try_lock()

Try me; don't wait forever.

std::timed_mutex m;
if (m.try_lock()) {
    // protected work
    m.unlock();
} else {
    // busy: skip, retry, or report
}

try_lock() returns immediately with success/failure. A timed mutex also supports waiting up to a deadline/duration.

Failure is not permission to touch shared data. Decide what the program should do when the lock is busy.

10DESIGN TRADE-OFF

Coarse vs fine-grained locking

Coarseone mutex for whole objectsimple, less parallelism
Fineseparate mutexes per resourcemore parallelism, more complexity

Start coarse-grained for correctness. Split locks only when profiling shows contention and you can define lock ownership/order clearly.

More locks mean more chances for deadlocks and inconsistent multi-lock operations.

11CLASS DESIGN

Thread-safe class and invariants

Keep my data valid as one unit.

class BankAccount {
    mutable std::mutex m;
    int balance = 0;
public:
    void deposit(int amount) {
        std::lock_guard lock(m);
        balance += amount;
    }
    bool withdraw(int amount) {
        std::lock_guard lock(m);
        if (balance < amount) return false;
        balance -= amount;
        return true;
    }
};

An invariant is a rule that must always hold, e.g. balance ≥ 0. Protect the whole check-and-update operation, not just individual lines.

Keep the mutex private. Public methods should preserve the class's invariant under concurrent calls.

12INTERVIEW DISTINCTIONS

Thread safety vs reentrancy

Thread-safeConcurrent calls are safe when used as documented.
ReentrantCan be safely entered again before a previous call finishes, including nested/signal-like contexts depending on definition.

A function can be thread-safe using a mutex but not reentrant if it deadlocks when called recursively or from a callback while the lock is held.

Thread safety is about concurrent access; reentrancy is about safely overlapping/nesting executions of the same code.

Simple checklist for LLD rounds
  • What data is shared?
  • What invariant must stay true?
  • Which exact operations form the critical section?
  • Who owns/acquires/releases each lock?
  • Can any path deadlock or call out while holding a lock?
  • Can we begin with one mutex and optimize later?

CHAPTER CHECKPOINT

Explain these in your own words

Try answering aloud before revealing the short answer.

Why is count++ not automatically safe?

It is a read-modify-write sequence; two threads can read the same old value and overwrite each other's update.

Why prefer lock_guard?

It releases the mutex automatically at scope exit, including early returns and exceptions.

When do I need unique_lock?

When you need deferred locking, manual unlock/relock, moving ownership, or condition-variable support.

How do I protect two variables that must agree?

Protect the complete invariant-changing operation under the same lock, not each variable independently.

What is a good first thread-safe class design?

Keep shared state private, use one private mutex, and make each public operation preserve the class invariant.
