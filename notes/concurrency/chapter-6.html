01ASYNC INTUITION

Do work now, collect the result later

Asynchronous programming separates starting work from receiving its result. A future is a handle to a result that may not be ready yet.

auto → future → get()

Async is a way to structure work; it does not automatically mean “create a new thread.”

02std::future

A one-time result that may arrive later

A future represents a value or exception produced by another operation. Usually only one consumer retrieves the result.

std::future<int> result = std::async(
  std::launch::async, [] { return 42; });
int answer = result.get();

get() retrieves the shared state’s result and makes the future invalid.

03std::promise

The producer manually fulfills a future

A promise lets one part of the program set a value or exception that another part receives through a future.

std::promise<int> p;
auto f = p.get_future();
p.set_value(7);
int value = f.get();

Useful when the producer’s work is not naturally expressed as one callable.

04std::async

Run a callable and return its future

std::async launches a function according to a launch policy and stores its result or exception in a future.

auto f = std::async(
  std::launch::async,
  [] { return compute(); });
auto result = f.get();

The returned future manages access to the asynchronous shared state.

05LAUNCH POLICIES

async vs deferred

launch::async requests asynchronous execution. launch::deferred stores the callable until a non-timed wait/get triggers it, on that thread.

std::async(std::launch::deferred,
  [] { return 10; });

The default policy may choose async or deferred. Specify a policy when behavior matters.

06std::packaged_task

Wrap a callable as a task with a future

packaged_task connects a callable’s result/exception to a future. You decide when and where to invoke the task.

std::packaged_task<int()> task(
  [] { return 5; });
auto f = task.get_future();
task();
int x = f.get();

A packaged_task can be placed into a queue and executed by a worker thread.

07std::shared_future

One result, multiple readers

A shared_future allows multiple consumers to observe the same shared result. Convert from future with share().

auto sf = std::async(
  std::launch::async, work).share();
// multiple readers:
auto a = sf.get();
auto b = sf.get();

Unlike future, shared_future’s get() can be called repeatedly.

08WAIT / GET / WAIT_FOR

Wait, retrieve, or check readiness

wait() blocks until ready. get() waits if needed and retrieves the result. wait_for() checks readiness after a duration.

if (f.wait_for(100ms) ==
    std::future_status::ready) {
  auto value = f.get();
}

wait_for() does not cancel the task when the timeout expires.

09EXCEPTIONS

Exceptions travel through the shared state

If the asynchronous callable throws, the exception is stored and rethrown when get() is called. Promise producers can set_exception().

try { auto value = f.get(); }
catch (const std::exception& e) {
  // handle worker failure
}

If nobody calls get(), the exception may never be observed by your code.

10COMPOSE TASKS

Build a pipeline from results

Conceptually, task composition means start a task, then schedule dependent work when its result is ready. Standard futures do not provide built-in .then() continuations.

auto f1 = std::async(
  std::launch::async, fetch);
auto data = f1.get();
auto f2 = std::async(
  std::launch::async,
  [data] { return transform(data); });

Real systems use executors, task graphs, callbacks, or libraries for non-blocking continuations.

11CANCELLATION

A future is not a cancellation button

std::future has no general cancel() operation. Cancellation is usually cooperative: share a stop flag/token and have the task check it.

std::atomic<bool> stop{false};
// worker periodically checks stop
stop.store(true);

C++20 std::jthread and stop_token provide a structured cooperative-stop mechanism.

12TIMEOUTS

Stop waiting ≠ stop the work

wait_for() can tell you a result is late. It does not terminate the worker. Design tasks to respond to cancellation or deadlines.

if (f.wait_for(1s) !=
    std::future_status::ready) {
  // timeout handling
}

Avoid abandoning work that still owns references or resources the caller assumes are gone.

13ASYNC VS THREAD POOL

One-off work vs many small tasks

std::async is convenient for a few independent operations. A thread pool reuses workers and controls queueing for many tasks.

pool.submit(taskA);
pool.submit(taskB);

For high-volume workloads, pool/executor APIs usually provide better control over concurrency and scheduling.

14FUTURE LIFETIME

Be aware of blocking behavior

A future returned by async with launch::async may block in its destructor if it is the last reference to an unfinished shared state.

{ auto f = std::async(
    std::launch::async, work);
  // scope exit can wait
}

Do not assume dropping the future detaches the work. Keep lifetime and shutdown behavior explicit.

15PICK THE TOOL

Match the abstraction to the job

Use future/promise for one result, packaged_task for queueable work, shared_future for multiple readers, and a pool for many tasks.

One result → future
Manual producer → promise
Queued callable → packaged_task
Many tasks → thread pool

Prefer clear ownership, explicit error handling, and cooperative cancellation.

CHAPTER CHECKPOINT

Explain these in your own words

Try answering aloud before revealing the short answer.

What is the difference between promise and future?

Promise is the producer-side handle that sets a result; future is the consumer-side handle that retrieves it.

Does wait_for timeout cancel work?

No. It only stops waiting after the duration. Cancellation must be designed separately, usually cooperatively.

async policy difference?

async requests asynchronous execution; deferred runs the callable later when a waiting operation triggers it.

When choose a thread pool?

For many tasks, worker reuse, bounded concurrency, and explicit scheduling/queue control.

How do exceptions reach the caller?

They are stored in the shared state and rethrown by future::get().
