01INTUITION

Don't keep checking—sleep until the condition may be ready

Is the queue ready? ...again?

I'll notify you when work arrives.

Without coordination, a thread may repeatedly check a shared variable (busy-waiting). A condition variable lets it sleep until another thread signals that something may have changed.

The condition variable is not the condition itself. The shared state/predicate tells us whether work is actually ready.

02WAIT MECHANICS

What does wait(lock) do?

1 · UnlockAtomically releases the mutex as it begins waiting.
2 · SleepBlocks until notified or spuriously awakened.
3 · Re-lockReacquires the mutex before wait returns.
std::unique_lock<std::mutex> lock(m);
cv.wait(lock); // unlock → block → lock again

wait() requires a std::unique_lock, not a lock_guard, because it must temporarily release and reacquire the mutex.

03PREDICATE

Predicate-based waiting

std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [&] { return ready; });
// equivalent:
while (!ready) cv.wait(lock);

The predicate overload checks the condition while holding the mutex. If false, it waits; after waking and reacquiring the lock, it checks again.

Think: “Wait until ready is true,” not “wait until I receive one notification.”

04NOTIFICATIONS

notify_one() vs notify_all()

notify_one()Wake one waiting thread. Good when one item enables one worker.
notify_all()Wake all waiters. Useful when a global state change may unblock everyone, such as shutdown.

Notifications are not queued messages. If nobody is waiting, the notification itself is gone—but a correctly protected predicate remains true for a later waiter.

Choose based on the predicate and work available; waking everyone unnecessarily can cause a thundering herd.

05WHY PREDICATES

Wakeup does not mean the condition is true

I woke up. Is there actually work?

Two reasons to re-check: a condition variable can wake spuriously, or another consumer may take the item before this thread reacquires the mutex.

cv.wait(lock, [&] { return !queue.empty() || stopping; });

The predicate overload is the safe default. Never write “wake = condition true.”

06PRODUCER–CONSUMER

One producer, one consumer

std::mutex m;
std::condition_variable cv;
std::queue<int> q;

void produce(int x) {
  { std::lock_guard<std::mutex> lock(m); q.push(x); }
  cv.notify_one();
}
int consume() {
  std::unique_lock<std::mutex> lock(m);
  cv.wait(lock, [&] { return !q.empty(); });
  int x = q.front(); q.pop();
  return x;
}

Producer changes shared state under the mutex, then notifies. Consumer waits for the queue predicate, then removes an item while holding the same mutex.

Notify after releasing the lock is a common pattern; notifying while locked can also be correct.

07BOUNDED QUEUE

Bounded blocking queue: wait for space and items

template<class T>
class BoundedQueue {
  std::mutex m;
  std::condition_variable not_empty, not_full;
  std::queue<T> q;
  const std::size_t capacity;
  bool stopping = false;
public:
  // push waits for q.size() < capacity
  // pop waits for !q.empty() || stopping
};

A bounded queue has two predicates: producers wait until there is room; consumers wait until there is an item (or shutdown begins).

Always mutate the queue and check its predicates under the same mutex.

08MULTIPLE WORKERS

Multiple producers and consumers

Several producers add items.

Several consumers compete for items.

One mutex protects queue structure and state. Each producer pushes one item and notifies; each consumer wakes, re-checks the predicate, and pops under the lock.

A notification wakes a thread, not reserves an item. The awakened consumer must still verify the queue.

For one item per push, notify_one() is usually appropriate. Use notify_all() when a state transition may satisfy many waiters.

09SHUTDOWN

Shutdown must change state and wake sleepers

void shutdown() {
  {
    std::lock_guard<std::mutex> lock(m);
    stopping = true;
  }
  not_empty.notify_all();
  not_full.notify_all();
}

Set the stopping flag while holding the mutex, then notify all waiters. Include shutdown in every wait predicate.

// consumer predicate
cv.wait(lock, [&] { return !q.empty() || stopping; });
if (q.empty() && stopping) return; // end worker

Without wake-up handling, a thread may remain blocked forever during destruction. Define whether shutdown drains queued work or discards it.

CHAPTER CHECKPOINT

Explain these in your own words

Try answering aloud before revealing the short answer.

Why does wait need unique_lock?

It must unlock the mutex while sleeping and lock it again before returning.

Why use a predicate?

Wakeups can be spurious, and notifications do not represent stored state. The predicate is the real condition.

When notify_one vs notify_all?

Use one when one waiter can proceed; use all when a state change may enable many waiters, such as shutdown.

What does a bounded queue coordinate?

Producers wait for capacity; consumers wait for available items; both predicates and queue operations share a mutex.

What must shutdown do?

Set a shutdown predicate under the lock, notify all blocked threads, and define drain/discard behavior.
