01DEADLOCK

Two threads, two locks, no progress

I hold A. Waiting for B.

I hold B. Waiting for A.

// Thread 1              // Thread 2
lock(A);                 lock(B);
lock(B); // waits        lock(A); // waits

A deadlock is a situation where threads are stuck waiting for resources held by one another, so none can continue.

A program may still be running and consuming little CPU while useful work is permanently blocked.

02FOUR CONDITIONS

Deadlock needs all four conditions

1 · Mutual exclusionA resource can be held by only one thread at a time.
2 · Hold and waitA thread holds one resource while waiting for another.
3 · No preemptionA resource cannot be forcibly taken away.
4 · Circular waitThreads form a cycle, each waiting for the next.

Break at least one condition to prevent this particular deadlock pattern. Circular wait is often the easiest to prevent through lock ordering.

03PREVENTION

Lock ordering: always acquire in the same order

A before B. Every time.

std::mutex A, B;

void task1() {
    std::lock_guard<std::mutex> a(A);
    std::lock_guard<std::mutex> b(B);
    // use both
}

If every code path acquires A before B, one thread cannot hold B while waiting for A. Establish a global order for locks and follow it everywhere.

The rule must cover all functions, callbacks, and code paths—not just one function.

04STANDARD LIBRARY

std::lock() and std::scoped_lock

// C++11: acquire both without lock-order deadlock
std::lock(A, B);
std::lock_guard<std::mutex> a(A, std::adopt_lock);
std::lock_guard<std::mutex> b(B, std::adopt_lock);

// C++17: simpler RAII form
std::scoped_lock locks(A, B);

std::lock uses a deadlock-avoidance algorithm to acquire all supplied mutexes. adopt_lock means “I already own this lock; manage its release.”

std::scoped_lock combines safe multi-lock acquisition with automatic release. Prefer it when available.

These help avoid deadlock while acquiring the listed locks; they cannot fix every possible deadlock involving other locks or external waits.

05LIVELock

Livelock: active, but not progressing

You go first!

No, you go first!

In a livelock, threads keep reacting to each other—retrying, yielding, or backing off—but never complete useful work.

Deadlock = stuck waiting. Livelock = moving/retrying without progress.

Prevention: add randomized or increasing backoff, avoid perfectly synchronized retries, and define a clear winner/ownership protocol.

06SCHEDULING

Starvation and fairness

Everyone gets the lock before me!

Starvation means a thread waits indefinitely because other threads repeatedly get the resource or CPU time.

Fairness is about whether waiting threads get a reasonable, predictable chance to proceed.

C++ mutexes do not generally promise FIFO fairness. If fairness matters, design an explicit queue/dispatcher or use a suitable synchronization strategy.

07PRIORITIES

Priority inversion

High priority HNeeds a lock held by L, so H blocks.
Low priority LHolds the lock but gets little CPU.
Medium priority MRuns often, delaying L and indirectly H.

Priority inversion occurs when a high-priority task is indirectly delayed by lower-priority work holding a resource.

Priority inheritance/ceiling protocols (where supported by the OS/runtime) can mitigate it. Keep critical sections short and avoid blocking I/O while holding locks.

08PERFORMANCE

Lock contention

Many threads, one narrow doorway.

Contention happens when many threads compete for the same lock. Threads spend time blocked or repeatedly attempting access instead of doing useful work.

Typical fixes: shorten the critical section, reduce shared mutable state, shard data, batch updates, or use a queue/actor design.

Don't replace mutexes with atomics or lock-free code just because contention exists. Measure first; simpler locking may still be best.

09CONDITION VARIABLES

Lost wakeup: the notification disappears

// Wrong idea: check without coordinating
if (!ready) cv.wait(lock); // notification may happen
                              // before this thread waits

A lost wakeup is when a notification happens before the waiter is actually waiting, and the waiter then sleeps despite the condition already being true.

Use a mutex-protected predicate and the predicate overload:

std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [&] { return ready; });

The condition/predicate is the truth. A notification is only a prompt to check it again. Update the predicate under the same mutex.

10CONDITION VARIABLES

Spurious wakeup: wake without your signal

I woke up—but is the queue actually non-empty?

A condition variable may wake a waiting thread even when no notification was sent. Also, another thread may consume the condition before this waiter reacquires the lock.

cv.wait(lock, [&] { return !queue.empty(); });
// equivalent idea:
while (queue.empty()) cv.wait(lock);

Never assume waking means the condition is true. Always re-check the predicate in a loop.

11DEBUGGING

Data race vs race condition · TSan

Data raceConflicting unsynchronized accesses to the same memory, at least one a write. In C++, this is undefined behavior.
Race conditionCorrectness depends on timing/order. It can exist even without a data race, e.g. wrong lock scope or check-then-act.
# Build with ThreadSanitizer (Clang/GCC)
g++ -std=c++17 -g -O1 -fsanitize=thread \
    -fno-omit-frame-pointer app.cpp -pthread -o app
./app

TSan detects many data races at runtime on executed paths. Reproduce the issue, run tests under TSan, inspect reports and lock ownership, and use debugger thread/backtrace views for hangs.

TSan is not a proof of correctness: it cannot find bugs on paths your tests never execute, and it does not diagnose every deadlock or logical race.

CHAPTER CHECKPOINT

Explain these in your own words

Try answering aloud before revealing the short answer.

What are the four necessary deadlock conditions?

Mutual exclusion, hold and wait, no preemption, and circular wait. Prevent deadlock by breaking at least one.

How does lock ordering prevent circular wait?

All code acquires locks in one global order, so a cycle of opposing lock dependencies cannot form.

Deadlock vs livelock vs starvation?

Deadlock: blocked forever. Livelock: active retries but no progress. Starvation: one thread keeps losing access to resources.

Why use a predicate with condition_variable::wait?

Notifications are not stored state; the predicate is the condition that must be true, and it must be checked under the lock.

What does TSan tell you?

It can report data races observed during a run, but it cannot prove all concurrency behavior is correct.
