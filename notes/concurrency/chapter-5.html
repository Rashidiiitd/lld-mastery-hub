01ATOMIC INTUITION

std::atomic: one indivisible operation

An atomic operation is observed as one indivisible action for that atomic object. It prevents data races on that object—but does not automatically make a multi-step algorithm correct.

std::atomic<int> count{0};
count.fetch_add(1);

Atomic is about indivisibility and ordering, not “make everything thread-safe.”

02LOAD / STORE

Read and write atomically

Atomic load/store avoid unsynchronized conflicting access to the atomic variable. Use them when a simple state/value is shared.

std::atomic<bool> ready{false};
ready.store(true);
if (ready.load()) { /* ... */ }

Default operations use sequential consistency. Explicit orders are an optimization/tool for expressing the needed guarantees.

03FETCH OPERATIONS

fetch_add() and fetch_sub()

These atomically update and return the old value. Useful for counters, ticket numbers, reference counts, and simple statistics.

std::atomic<int> n{0};
int old = n.fetch_add(1);
n.fetch_sub(1);

The increment is atomic; a separate “if then increment” sequence is not automatically atomic.

04COMPARE-AND-SWAP

Update only if the value is still what I expect

CAS compares the current value with an expected value. If equal, it writes desired; otherwise it updates expected with the observed value.

int expected = 0;
if (state.compare_exchange_strong(expected, 1)) {
  // changed 0 → 1
}

CAS is the building block for many lock-free algorithms. The surrounding algorithm still needs careful reasoning.

05MEMORY MODEL

Atomicity is not the same as visibility/order

C++ memory orders describe what one thread is allowed to observe about operations in other threads. Think: value update + ordering guarantees.

std::atomic<int> x{0};
// memory order is specified per operation

Start with the default seq_cst. Relax ordering only after proving which communication/order is required.

06RELAXED

Atomic value, no ordering promise for other data

memory_order_relaxed guarantees atomicity and a coherent modification order for that atomic object, but does not publish unrelated data.

counter.fetch_add(1,
  std::memory_order_relaxed);

Good for independent counters/statistics. Not enough by itself to publish a non-atomic payload safely.

07ACQUIRE / RELEASE

Publish data through a flag

Release store and acquire load can establish synchronizes-with when the acquire reads from the release (or its release sequence). Then prior writes become visible.

payload = 42;
ready.store(true, std::memory_order_release);
// reader:
if (ready.load(std::memory_order_acquire))
  use(payload);

The payload must not be concurrently modified unsafely. The acquire must observe the release-published flag.

08SEQ_CST

A single global order for seq_cst operations

memory_order_seq_cst adds a total order among sequentially consistent operations, consistent with each thread’s order. It is easiest to reason about.

flag.store(true, std::memory_order_seq_cst);
if (flag.load(std::memory_order_seq_cst)) { /* ... */ }

It is the default and a good starting point. It may be stronger than necessary, but correctness comes first.

09WEAK VS STRONG CAS

Weak may fail spuriously

compare_exchange_weak may report failure even when expected matched; it is designed for retry loops. strong does not fail spuriously.

int expected = 0;
while (!state.compare_exchange_weak(expected, 1)) {
  expected = 0; // reset if retrying same target
}

On failure, expected is overwritten with the current value. Re-check or recompute it deliberately.

10HAPPENS-BEFORE

The ordering chain that makes data safe to observe

If A happens-before B, effects before A are visible to B under the C++ model. Synchronizes-with edges (like release/acquire) can create happens-before chains.

Thread A: write payload; release-store flag
Thread B: acquire-load flag; read payload

Without a happens-before relation, conflicting non-atomic accesses may be a data race (undefined behavior).

11ATOMIC FLAG

Smallest atomic building block

std::atomic_flag is guaranteed lock-free and supports test_and_set/clear. It can implement a simple spinlock, but spinning wastes CPU under contention.

std::atomic_flag f = ATOMIC_FLAG_INIT;
while (f.test_and_set(std::memory_order_acquire)) {}
// critical section
f.clear(std::memory_order_release);

C++20 adds wait/notify operations. Prefer mutexes for ordinary critical sections.

12PROGRESS GUARANTEES

Lock-free ≠ wait-free ≠ obstruction-free

Obstruction-free: a thread completes if it runs alone. Lock-free: system-wide progress—some operation completes. Wait-free: every operation completes in a bounded number of its own steps.

These are algorithm guarantees,
not synonyms for “uses atomics.”

A lock-free algorithm can still starve an individual thread. Wait-free is the strongest of these guarantees.

13ABA PROBLEM

A value changed A → B → A, so CAS misses the history

CAS sees the same value A and assumes nothing changed, even though the object may have been removed/reused in between. Common in lock-free stacks.

Observed pointer: A
Other thread: A → B → A
CAS still sees A

Mitigations include tagged/versioned pointers, hazard pointers, or epoch-based reclamation—depending on the algorithm.

14SPINLOCKS

Keep retrying until the lock becomes free

A spinlock loops on an atomic flag rather than sleeping. It may be reasonable for extremely short waits in controlled environments.

while (flag.test_and_set(std::memory_order_acquire)) {
  // spin
}
// critical section
flag.clear(std::memory_order_release);

Bad for long waits, oversubscribed CPUs, or code that may block. A mutex can yield/sleep instead.

15FALSE SHARING

Different variables, same cache line

Two threads update separate variables that happen to share a cache line. Cache-coherence traffic makes both updates slow.

Thread A updates counterA
Thread B updates counterB
Same cache line → ping-pong

Measure first. Padding/alignment or per-thread counters can help; layout changes should be benchmarked.

16ATOMICS OR MUTEX?

Choose the simplest correct synchronization

Use atomics for simple independent state/counters or carefully designed lock-free algorithms. Use mutexes for compound invariants and multi-step operations.

Mutex: protect balance + rules together
Atomic: increment a standalone counter

Atomics do not automatically protect a group of variables or make check-then-act sequences indivisible.

17VOLATILE

volatile is not thread synchronization

In C++, volatile affects certain compiler treatment of accesses, but it does not make operations atomic or establish inter-thread ordering.

volatile int ready; // not a thread-safe flag
std::atomic<bool> ready{false};

Use atomics/mutexes for threads. volatile has specialized uses such as certain memory-mapped I/O, not general concurrency.

CHAPTER CHECKPOINT

Explain these in your own words

Try answering aloud before revealing the short answer.

What does relaxed guarantee?

Atomicity and per-object modification order, but no synchronization/order for unrelated memory.

How does release/acquire publish data?

A release operation synchronizes with an acquire that observes it; preceding writes become visible to the acquiring thread.

What is happens-before?

An ordering relation that makes prior effects visible and helps establish data-race freedom.

Weak vs strong CAS?

Weak may fail spuriously and is typically used in retry loops; strong does not spuriously fail.

When prefer mutex over atomics?

When protecting compound invariants, multiple fields, or complex critical sections. Prefer the simplest correct design.
