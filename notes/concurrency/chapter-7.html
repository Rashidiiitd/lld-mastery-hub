Thread Pool
Design & Implementation

A must-know LLD component: queue work, reuse workers, deliver results, and shut down safely.

01ARCHITECTURE

A pool is a reusable team of workers

Submit tasks to a queue; worker threads repeatedly take tasks and execute them. The pool owns worker lifetime and coordinates shutdown.

Submit → queue → worker → execute → result

It avoids creating a new thread for every small task and gives control over concurrency.

02WORKERS + TASK QUEUE

Separate scheduling from execution

A queue stores pending work. Workers wait for tasks, remove one safely, then execute it outside the queue lock.

lock queue
pop task
unlock
run task

Never hold the queue mutex while executing arbitrary user code.

03MUTEX + CONDITION VARIABLE

Sleep until work arrives or shutdown begins

Workers wait on a predicate: queue is non-empty OR stopping. Producers enqueue under the mutex, then notify.

cv.wait(lock, [&]{
  return stopping || !tasks.empty();
});

Predicate waiting handles spurious wakeups and checks state while protected by the mutex.

04BASIC IMPLEMENTATION

The core worker loop

A minimal pool has a task queue, mutex, condition variable, stop flag, and worker vector. Workers exit only when stopping and no work remains.

while (true) {
  wait for stop or work;
  if (stop && queue.empty()) return;
  take task;
  run task;
}

This is the graceful-drain behavior: queued work completes before workers exit.

05GENERIC SUBMIT

Accept arbitrary callables and arguments

A templated submit stores the callable and arguments in a task wrapper, enqueues it, and returns a future for the result.

template<class F, class... Args>
auto submit(F&& f, Args&&... args);

Use decay/capture or bind carefully so arguments have safe ownership and move-only values can be supported.

06FUTURE RESULTS

Return values through shared state

submit determines the callable’s result type, creates a packaged_task, obtains its future, queues execution, and returns the future.

std::packaged_task<R()> task(...);
auto result = task.get_future();
queue task wrapper;
return result;

The task wrapper can be std::function only if the stored target is copyable; move-only task wrappers need a different type-erasure strategy.

07PACKAGED_TASK

Connect task execution to result delivery

packaged_task catches the callable’s exception and stores either value or exception in the shared state. future::get() rethrows it.

worker executes packaged_task
caller: future.get()

The worker loop should still catch unexpected exceptions from task wrappers so one bad task cannot terminate the worker.

08SHUTDOWN MODES

Graceful drain vs immediate discard

Graceful shutdown stops accepting new tasks and lets queued tasks finish. Immediate shutdown requests stop and discards pending tasks (running tasks usually cannot be forcibly killed safely).

shutdown(drain=true)
shutdown(drain=false)

Specify what happens to futures for discarded tasks—e.g. set an exception/cancellation result rather than leaving them unresolved.

09SUBMIT AFTER STOP

Reject new work deterministically

Check the stopping state while holding the same mutex used to enqueue. If stopped, throw or return an explicit error.

lock
if (stopping) reject
queue.push(task)
unlock
notify_one

Checking stop outside the lock can race with shutdown and accidentally accept work after shutdown begins.

10POOL SIZING

CPU-bound vs I/O-bound

CPU-bound tasks often start near hardware_concurrency. I/O-bound tasks may benefit from more workers because some are blocked—but excessive threads add overhead.

CPU work: around core count
I/O work: tune to workload

hardware_concurrency() can return 0 and is only a hint. Benchmark with realistic load.

11BOUNDED QUEUE

Backpressure protects the system

A bounded queue limits pending tasks. When full, submit can block, reject, or use timed submission—each policy changes system behavior.

capacity reached →
block / reject / timeout

Avoid blocking submit from a worker in the same saturated pool; it can deadlock through pool exhaustion.

12TASK PRIORITIES

Choose urgent work first

A priority queue can order tasks by priority, but a constant stream of high-priority work can starve low-priority tasks.

priority queue
high → medium → low

Use aging, quotas, or fair scheduling if every class needs progress.

13WORK STEALING

Idle workers take work from busy workers

Workers keep local deques; an idle worker steals from another worker, improving load balance for fork/join workloads.

local queue → execute
empty → steal

More complex than a single shared queue. Consider only when profiling shows queue contention or imbalance.

14STARVATION + EXHAUSTION

Workers can be busy but the system can still stall

Blocking tasks can occupy every worker while waiting for tasks that are queued in the same pool. Long tasks can also starve short tasks.

all workers wait
for queued pool work
→ deadlock

Avoid synchronous nested waits on the same bounded pool; separate blocking work or use continuations.

15TEST THE POOL

Test lifecycle and failure paths

Test task results, exceptions, concurrent submissions, shutdown races, rejection after stop, queue capacity, and repeated construction/destruction.

many submitters
+ shutdown
+ futures + errors

Use deterministic barriers/latches where possible, stress tests, ThreadSanitizer, and time-bounded tests to catch hangs.

CHAPTER CHECKPOINT

Explain these in your own words

Try answering aloud before revealing the short answer.

What are the core pool components?

Worker threads, task queue, mutex, condition variable, shutdown state, and a submission interface.

Why execute tasks outside the queue lock?

User tasks may block, throw, or submit more work. Holding the lock would stall all queue operations and can deadlock.

How does submit return a result?

Wrap the callable in packaged_task, obtain its future, enqueue a wrapper that invokes the task, then return the future.

Graceful vs immediate shutdown?

Graceful shutdown drains queued work. Immediate shutdown discards pending work and must define how affected futures are completed.

What is pool exhaustion?

All workers are occupied—often blocked waiting for work queued to the same pool—so no worker remains to execute that work.
