OOPQ01

What is the difference between class and struct in C++?

Try to explain the language-level difference, not just how you usually use them.

Show explanation & interview answer

The key difference is the default access level: members and base classes of a class are private by default; for a struct, they are public by default. Both can have constructors, methods, inheritance, and access specifiers.

class User { int id; };       // id is private
struct Point { int x, y; };   // x and y are public

Interview answer: They have essentially the same capabilities. I generally use struct for simple public data aggregates and class when encapsulation is central; that is a convention, not a restriction.

Follow-up: What is the default inheritance access for each? Class inheritance is private by default; struct inheritance is public by default.

Memory & lifetimeQ02

What is the difference between stack and heap memory?

Start with storage duration and ownership; avoid saying only that one is faster.

Show explanation & interview answer

“Stack” usually refers to automatic storage used for local variables, whose lifetime follows scope. “Heap” usually refers to dynamic storage, where an object's lifetime is managed explicitly or through an owning abstraction. The C++ standard describes storage duration categories; stack and heap are common implementation terms.

void f() {
    Widget local;                       // automatic lifetime
    auto p = std::make_unique(); // dynamic object, RAII owner
} // both objects are cleaned up here

Interview answer: Prefer automatic objects and RAII. Use dynamic allocation when lifetime or polymorphic ownership requires it, and represent ownership with smart pointers rather than raw owning pointers.

Follow-up: What happens if you return a pointer to a local variable? It dangles after the function returns.

Copy & moveQ03

Shallow copy vs deep copy?

What exactly gets copied when an object contains a pointer?

Show explanation & interview answer

A member-wise copy copies each member's value. If a member is a raw pointer, that copies the address, not the pointed-to object; both objects may then refer to the same resource. A deep copy duplicates the owned resource so each object has independent ownership.

// Conceptual example
struct Bad {
    int* p;
    // default copy copies the address
};

// Prefer value members or a suitable owning type:
struct Good {
    std::vector values;
};

Interview answer: Shallow copying is not inherently wrong if shared identity is intended. The danger is accidental shared ownership or double deletion. Prefer Rule of Zero types such as std::vector and std::string; write custom copy behavior only when resource semantics require it.

Follow-up: Explain the Rule of Three, Five, and Zero.

Copy & moveQ04

Explain the Rule of Three, Five, and Zero.

Why do these rules exist, and how do modern C++ types help?

Show explanation & interview answer
  • Rule of Three: if a class needs a custom destructor, copy constructor, or copy-assignment operator, it likely needs all three.
  • Rule of Five: modern C++ adds move constructor and move-assignment operator to those five special member functions.
  • Rule of Zero: design types using members that already manage their own resources, so custom special members are unnecessary.

Interview answer: The rules help keep ownership and copying consistent. My default is Rule of Zero with RAII members; I implement the Rule of Five only for a type that directly manages a resource.

Follow-up: Why can declaring a destructor affect implicit move generation? Certain user-declared special members suppress implicit move operations, so the exact declarations matter.

Copy & moveQ05

What are move semantics and what does std::move do?

Does std::move itself move data?

Show explanation & interview answer

std::move is a cast that makes an expression eligible to bind to move-aware overloads. It does not move resources by itself. A move constructor or move assignment operator may transfer a resource from the source object.

std::string source = "hello";
std::string destination = std::move(source);
// destination gets the value; source remains valid,
// but its exact value is unspecified.

Interview answer: Move semantics can avoid expensive resource duplication when the source can be left in a valid moved-from state. I avoid using the source's old value unless its contract guarantees what that value is.

Follow-up: Why should we not blindly call std::move on every variable? It can inhibit useful optimizations and may select a different overload or leave an object moved-from.

OOPQ06

Why should a polymorphic base class often have a virtual destructor?

Consider deleting a derived object through a base pointer.

Show explanation & interview answer

If a derived object is deleted through a base pointer, the base class needs a virtual destructor for well-defined polymorphic destruction. Without it, that delete expression has undefined behavior when the static and dynamic types differ in this way.

struct Base {
    virtual ~Base() = default;
};
struct Derived : Base {
    ~Derived() override = default;
};

std::unique_ptr p = std::make_unique();

Interview answer: If a class is intended to be used polymorphically and clients may destroy derived instances through a base pointer, its destructor should be virtual. A base not designed for polymorphic deletion may instead make the destructor protected and non-virtual.

Follow-up: Can a constructor be virtual? No; virtual dispatch requires an already-constructed object.

PolymorphismQ07

Overloading vs overriding vs name hiding?

Compare where each is resolved and what signatures mean.

Show explanation & interview answer
  • Overloading: same name, different parameter lists; overload resolution happens at compile time.
  • Overriding: a derived class provides a matching virtual function implementation; dispatch can happen at runtime.
  • Name hiding: a declaration in a derived scope can hide base overloads with the same name. using Base::f; can bring them into scope.

Interview answer: Overloading is selecting between function signatures; overriding replaces a virtual behavior in a derived type; name hiding is a scope lookup rule and can occur even when signatures differ.

Follow-up: Why use the override keyword? It makes the compiler verify that the function actually overrides a base virtual function.

PolymorphismQ08

What is a pure virtual function and an abstract class?

How does an interface help decouple a caller from implementations?

Show explanation & interview answer

A pure virtual function is declared with = 0. A class with at least one pure virtual function is abstract and cannot be instantiated directly. Derived concrete classes must provide the required overrides.

struct PaymentMethod {
    virtual ~PaymentMethod() = default;
    virtual bool pay(int cents) = 0;
};

struct CardPayment final : PaymentMethod {
    bool pay(int cents) override { return cents > 0; }
};

Interview answer: An abstract interface describes a contract. Code can depend on that contract rather than a specific implementation, making substitution, testing, and extension easier.

Follow-up: Can a pure virtual function have a definition? Yes, but a class with that pure virtual declaration remains abstract.

Memory & lifetimeQ09

unique_ptr vs shared_ptr vs weak_ptr?

Choose based on ownership semantics, not convenience.

Show explanation & interview answer
  • unique_ptr: exclusive ownership; cheap, movable, not copyable.
  • shared_ptr: shared ownership through a reference-counted control block.
  • weak_ptr: non-owning observer of an object managed by shared_ptr; lock it to obtain a temporary owning reference.

Interview answer: I use unique_ptr by default for dynamic ownership. I use shared_ptr only when lifetime is genuinely shared, and weak_ptr to observe shared objects without extending lifetime or creating ownership cycles.

Follow-up: Does shared_ptr make the pointed-to object thread-safe? No. It protects its control block's reference counting, not arbitrary concurrent access to the object.

Memory & lifetimeQ10

Pointer vs reference in C++?

Think about nullability, reseating, and lifetime guarantees.

Show explanation & interview answer

A pointer stores an address, can be null, and can be reassigned to point elsewhere. A reference is an alias initialized to refer to an object and cannot be reseated. Neither automatically extends the lifetime of an ordinary referenced object in every situation; dangling pointers and references are both possible.

Interview answer: Use a reference when an object is required and null is not a valid state; use a pointer when absence or reseating is part of the API. Ownership should be represented separately and clearly.

Follow-up: What is a dangling reference? A reference that refers to an object whose lifetime has ended.

STL & languageQ11

vector vs list — which should you choose?

Big-O is only part of the decision. Think about locality and iterator invalidation.

Show explanation & interview answer

vector stores elements contiguously, offers constant-time random access and amortized constant-time append, and has strong cache locality. Reallocation invalidates pointers, references, and iterators to its elements. list is a doubly linked list with constant-time insertion/erasure at a known iterator, but no random access and higher per-element overhead.

Interview answer: I choose vector by default for most sequences because locality and simplicity matter. I choose list only when its specific iterator-stability and insertion/erasure properties are needed and measured.

Follow-up: What does reserve() do? It requests capacity without changing the vector's size and can reduce future reallocations.

STL & languageQ12

map vs unordered_map?

Compare ordering guarantees, complexity, and worst-case behavior.

Show explanation & interview answer

map keeps keys ordered and commonly provides logarithmic lookup/insert/erase using a balanced tree. unordered_map uses hashing and provides average constant-time lookup/insert/erase, but worst-case operations can be linear and iteration order is unspecified.

Interview answer: Use map when sorted traversal or ordered-range operations are needed. Use unordered_map when key order is irrelevant and average lookup performance is appropriate; account for hashing quality and worst cases.

Follow-up: What must a custom hash and equality function satisfy? Equal keys must produce equal hash values.

STL & languageQ13

Explain const int*, int* const, and const int* const.

Read the declaration from the variable name outward.

Show explanation & interview answer
  • const int* p: pointer to const int; cannot modify the int through p, but can reseat p.
  • int* const p: const pointer to int; cannot reseat p, but can modify the int through it.
  • const int* const p: const pointer to const int; neither can be changed through this declaration.

Interview answer: Const-correctness documents and enforces which parts of an API may mutate state. It improves readability and catches accidental writes at compile time.

Follow-up: What does a const member function promise? It cannot modify non-mutable data members through the implicit object parameter.

STL & languageQ14

What are templates and when are they instantiated?

How are templates different from runtime polymorphism?

Show explanation & interview answer

Templates let code be parameterized by types and compile-time values. The compiler forms specializations when a template is instantiated for particular arguments. This supports generic algorithms and compile-time checking without requiring virtual dispatch for that abstraction.

template<typename T>
T maximum(T a, T b) {
    return a < b ? b : a;
}

Interview answer: Templates enable compile-time generic programming and can support static polymorphism. Virtual functions support runtime dispatch through a base interface. Each has different flexibility, compile-time, binary-size, and coupling trade-offs.

Follow-up: What is template specialization? A customized implementation for specific template arguments.

ConcurrencyQ15

What is a data race, and how is it different from a race condition?

One is a specific language-level correctness problem; the other is a broader timing problem.

Show explanation & interview answer

A data race occurs when conflicting accesses to the same memory location happen concurrently, at least one is a write, the accesses are not properly ordered, and neither is atomic. In C++, a data race causes undefined behavior. A race condition is broader: correctness depends on timing or ordering, even when there is no data race.

Interview answer: Use a mutex to protect compound invariants, or atomics when the state and memory-ordering requirements are understood. Thread-safe individual operations do not automatically make a multi-step operation atomic.

Follow-up: Is i++ thread-safe for a shared ordinary integer? No. Concurrent unsynchronized increments can form a data race.

ConcurrencyQ16

lock_guard vs unique_lock?

Why does RAII matter when acquiring a mutex?

Show explanation & interview answer

lock_guard is a small scope-based lock wrapper: it locks on construction and unlocks on destruction. unique_lock is more flexible: it can defer locking, unlock and relock, and work with condition variables; it has a little more state and overhead.

std::mutex m;
{
    std::lock_guard<std::mutex> lock(m);
    // protected work
} // automatically unlocks

Interview answer: RAII ensures lock release on normal scope exit and exceptions. I use lock_guard for simple critical sections and unique_lock when deferred locking or condition-variable integration is needed.

Follow-up: How can deadlocks be reduced? Use consistent lock ordering, minimize lock scope, and consider std::scoped_lock for locking multiple mutexes safely.

FundamentalsQ17

What happens when a C++ program is compiled and executed?

Walk through the pipeline from source code to a running process.

Show explanation & interview answer

The usual pipeline is preprocessing, compilation to assembly or an intermediate form, assembling to object files, linking, loading, and execution. Exact toolchain steps vary.

Interview answer: The preprocessor handles directives, the compiler checks and translates C++, the assembler creates object code, and the linker resolves symbols across translation units and libraries. The operating system then loads the executable.

Follow-up: What causes an undefined reference? Often a declaration exists, but the corresponding definition is missing from the linked objects or libraries.

FundamentalsQ18

Compile-time polymorphism vs runtime polymorphism?

Compare templates and overloads with virtual dispatch.

Show explanation & interview answer

Compile-time polymorphism includes function/operator overloading and templates; the compiler selects or instantiates behavior at compile time. Runtime polymorphism commonly uses virtual functions and dynamic dispatch based on the object's dynamic type.

Trade-off: Static polymorphism can enable inlining but may increase code size. Runtime polymorphism supports substitution through a common base interface but typically requires dynamic dispatch.

Follow-up: Is function overloading runtime polymorphism? No; overload resolution is performed at compile time.

OOPQ19

How do vtables and vptrs usually implement virtual dispatch?

Explain the common implementation, and distinguish it from what the standard guarantees.

Show explanation & interview answer

Common implementations use a virtual table containing function pointers for a class's virtual functions, and a hidden pointer in polymorphic objects that helps locate the relevant table. A virtual call uses this mechanism to select the final overrider.

Important nuance: The C++ standard specifies behavior, not a mandatory vtable/vptr implementation. Layout and dispatch details are ABI/compiler dependent.

Follow-up: Does every C++ object contain a vptr? No, not generally; it is commonly present in polymorphic objects.

PolymorphismQ20

What is object slicing, and how do you avoid it?

What gets lost when a derived object is copied into a base object by value?

Show explanation & interview answer

Object slicing occurs when a derived object is copied into a base-class object by value. The resulting base object contains only the base subobject; derived-specific state and behavior are sliced away.

struct Base { virtual int value() const { return 1; } };
struct Derived : Base { int value() const override { return 2; } };
Derived d;
Base b = d;          // slicing: b is a Base object
Base& ref = d;       // no slicing

Interview answer: Use references, pointers, or suitable smart pointers for polymorphic access, rather than storing derived objects as base values.

OOPQ21

What is the diamond problem, and how does virtual inheritance help?

Draw the inheritance diamond and count the base subobjects.

Show explanation & interview answer

If two intermediate classes inherit from the same base and a final class inherits from both, the final object can contain two base subobjects. This can make member access ambiguous and duplicate shared base state.

struct A { int id; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {}; // one shared A subobject

Interview answer: Virtual inheritance makes the most-derived object share one virtual base subobject. It adds construction complexity: the most-derived class is responsible for initializing virtual bases.

OOPQ22

Public vs protected vs private inheritance?

How does inheritance access affect the derived class's public interface?

Show explanation & interview answer

Public inheritance preserves public base members as public and protected as protected. Protected inheritance maps both public and protected base members to protected in the derived interface. Private inheritance maps both to private. Base-class private members remain inaccessible directly in the derived class.

Interview answer: Public inheritance usually models an “is-a” substitutable relationship. Private inheritance can express implementation reuse, though composition is often clearer.

Follow-up: What are the defaults? Class inheritance is private by default; struct inheritance is public by default.

PolymorphismQ23

What happens when a virtual function is called in a constructor or destructor?

Why is calling an overridable function from construction risky?

Show explanation & interview answer

During construction and destruction, virtual dispatch does not call an override in a more-derived class whose portion is not yet constructed or has already been destroyed. The call resolves within the class currently being constructed or destroyed.

Interview answer: Avoid relying on derived overrides from base constructors or destructors; the derived state may not be initialized or may already be gone.

Follow-up: Why can a pure virtual call here be problematic? The expected derived implementation may not participate in dispatch during that phase.

MemoryQ24

What is a memory leak, and how do you prevent or diagnose one?

Explain the ownership bug before naming a tool.

Show explanation & interview answer

A leak occurs when dynamically allocated resources remain allocated after the program no longer has a usable way to release them. Common causes include lost owning pointers, missing cleanup, and ownership cycles.

Prevention: Prefer RAII and standard containers/smart pointers. Diagnosis: AddressSanitizer/LeakSanitizer and tools such as Valgrind can help identify leaks and invalid memory accesses.

Follow-up: Can a program have no leaks but still use invalid memory? Yes; use-after-free and buffer overflows are separate bugs.

MemoryQ25

What is the difference between new/delete and malloc/free?

Compare allocation, object lifetime, and type safety.

Show explanation & interview answer

malloc allocates raw storage and returns a void*; it does not invoke a C++ constructor. free releases that storage without invoking a C++ destructor. new allocates storage and constructs an object; delete destroys the object and releases storage.

Interview answer: In modern C++, prefer automatic objects, containers, and smart pointers. Never mix allocation/deallocation families, such as new with free.

Follow-up: What is the matching deallocation for new[]? Use delete[].

MemoryQ26

Dangling pointer vs wild pointer?

Which one refers to an object whose lifetime has ended?

Show explanation & interview answer

A dangling pointer used to point to an object whose lifetime has ended or whose storage is no longer valid. “Wild pointer” is an informal term often used for an uninitialized pointer containing an indeterminate value. Both must not be dereferenced.

Prevention: Initialize pointers, use RAII and smart pointers, and avoid returning addresses or references to local objects.

Follow-up: Does assigning nullptr to one pointer fix other aliases to the same freed object? No; other aliases may still dangle.

Copy & MoveQ27

Explain lvalues, prvalues, and xvalues.

Use expression categories to explain overload selection and moves.

Show explanation & interview answer

An lvalue identifies an object with identity; a prvalue is a value computation that initializes an object or produces a value; an xvalue identifies an object whose resources may be reused. “Rvalue” is the umbrella category that includes prvalues and xvalues.

int x = 1;
int& a = x;            // lvalue reference
int&& b = 2;           // rvalue reference
int&& c = std::move(x); // xvalue expression

Follow-up: What category is the expression x in std::move(x)? The expression x itself is an lvalue; std::move(x) is an xvalue.

Copy & MoveQ28

Copy semantics vs move semantics?

When is transferring resources preferable to duplicating them?

Show explanation & interview answer

Copy semantics create a logically independent value or shared state according to the type's contract. Move semantics allow a type to efficiently transfer resources from an object that can be left in a valid but unspecified state.

Example: Moving a std::vector can transfer its buffer instead of allocating and copying every element, though exact performance depends on allocator and type details.

Follow-up: Are all moves cheap? No. A type's move operation can still perform expensive work, and some types may copy instead.

Copy & MoveQ29

What are perfect forwarding and std::forward?

Why does a forwarding reference preserve the caller's value category?

Show explanation & interview answer

In a deduced template context, T&& can be a forwarding reference. Reference collapsing lets it bind to lvalues and rvalues. std::forward<T> conditionally casts the argument to preserve the value category deduced for T.

template
void relay(T&& value) {
    consume(std::forward(value));
}

Interview answer: Perfect forwarding lets wrappers pass arguments onward without unnecessarily converting lvalues into rvalues or losing move opportunities.

Follow-up: Is every T&& a forwarding reference? No; for example, a non-template parameter declared as Widget&& is an rvalue reference.

STLQ30

What is the difference between const and constexpr?

Is every const variable usable in a constant expression?

Show explanation & interview answer

const prevents modification through that name after initialization; it does not automatically mean the initializer is a compile-time constant expression. constexpr declares that a variable or function can participate in constant evaluation when the requirements are met.

const int runtimeValue = readInput();
constexpr int answer = 42;

Follow-up: Can a constexpr function run at runtime? Yes. It can be evaluated at compile time when used in a constant-expression context, or at runtime otherwise.

STLQ31

What is the difference between auto and decltype?

Think about how each deduces a type and preserves references.

Show explanation & interview answer

auto generally deduces a type similarly to template argument deduction and typically drops top-level const and references unless you request them with forms such as const auto& or auto&. decltype(expression) follows rules based on the declared entity or expression category and can preserve references.

int x = 0;
auto a = x;        // int
auto& b = x;       // int&
decltype(x) c = x; // int

Follow-up: What does decltype((x)) produce for an lvalue x? int&.

STLQ32

What is SFINAE?

Why can one invalid template substitution remove an overload instead of failing compilation immediately?

Show explanation & interview answer

SFINAE means “Substitution Failure Is Not An Error.” In certain template argument substitution contexts, a substitution failure removes that candidate from overload resolution instead of making the entire program ill-formed.

Use: It historically enabled conditional template overloads and type traits. In modern C++20, concepts and requires clauses often express constraints more clearly.

Follow-up: Does SFINAE hide every compiler error inside a template body? No; it applies to specific substitution contexts, not arbitrary errors in instantiated function bodies.

STLQ33

Explain stack unwinding and exception-safety guarantees.

What happens to local RAII objects when an exception propagates?

Show explanation & interview answer

When an exception propagates out of a scope, destructors of fully constructed automatic objects are called in reverse construction order. This is stack unwinding, and it is why RAII is essential.

  • No-throw guarantee: the operation does not let exceptions escape.
  • Strong guarantee: failure leaves observable state unchanged.
  • Basic guarantee: invariants remain valid and resources are not leaked.

Follow-up: Why should destructors generally not throw during unwinding? A second escaping exception can lead to std::terminate.

STLQ34

std::vector vs std::list: when would you choose each?

Include cache locality, iterator stability, and actual operation costs.

Show explanation & interview answer

std::vector stores elements contiguously, offers fast random access, and usually has excellent cache locality; inserting in the middle can shift elements and growth can reallocate. std::list is a doubly linked list with stable iterators to non-erased elements, but has per-node allocation and poor locality.

Interview answer: I default to vector unless measured requirements or iterator-stability needs justify another container. List insertion is O(1) only when the insertion position is already known; finding it is still linear.

STLQ35

std::map vs std::unordered_map?

Compare ordering, complexity, and guarantees.

Show explanation & interview answer

std::map maintains sorted keys, typically using a balanced search tree, with O(log n) search, insertion, and erasure. std::unordered_map is hash-based with average O(1) lookup and insertion, but worst-case O(n), and does not maintain sorted iteration order.

Choose: Use map for ordered traversal, range queries, or predictable logarithmic complexity; use unordered_map when hash lookup fits and ordering is unnecessary.

Follow-up: What must a custom hash/equality pair satisfy? Keys considered equal must produce equal hash values.

STLQ36

How does vector grow when size reaches capacity?

Why is push_back amortized O(1), not always O(1)?

Show explanation & interview answer

When capacity is exhausted, a vector typically allocates a larger contiguous buffer, constructs or moves/copies elements into it, and releases the old buffer. The growth factor is implementation-dependent.

Complexity: A reallocation can cost O(n), but geometric growth makes repeated end insertions amortized O(1). Reallocation invalidates pointers, references, and iterators to elements.

Follow-up: What does reserve(n) do? It requests capacity for at least n elements without changing size.

STLQ37

What is iterator invalidation?

Why can an iterator that once worked become unsafe after a container operation?

Show explanation & interview answer

Iterator invalidation occurs when a container operation makes existing iterators, pointers, or references no longer valid. For example, vector reallocation invalidates all element iterators and references; erasing a vector element invalidates those at or after it. Associative map insertion generally preserves existing iterators; erasing invalidates those to erased elements.

Interview answer: Know the guarantees for the specific container and operation. Never dereference an invalidated iterator; use the iterator returned by erase where applicable.

Follow-up: Can unordered_map rehash invalidate iterators? Yes; rehash invalidates iterators, though references and pointers to elements are preserved.

STLQ38

push_back vs emplace_back?

Does emplace_back always perform better?

Show explanation & interview answer

push_back inserts an existing object by copy or move. emplace_back forwards constructor arguments to construct an element in place at the end.

std::vector v;
v.push_back(std::string("hello"));
v.emplace_back("world");

Interview answer: emplace_back can avoid a temporary when passing constructor arguments, but it is not automatically faster or clearer in every case. Both can trigger vector reallocation.

Follow-up: What changed in modern C++ regarding emplace_back's return value? Since C++17, it returns a reference to the inserted element.

STLQ39

How does std::unordered_map work internally?

Explain hashing, collisions, load factor, and rehashing.

Show explanation & interview answer

A hash function maps a key to a hash value used to select a bucket. Collisions occur when different keys map to the same bucket; implementations use a collision-resolution strategy such as chaining. Equality comparison distinguishes keys within a bucket.

Complexity: Lookup and insertion are average O(1), but can degrade to O(n) in the worst case. As the load factor grows, the container may rehash into more buckets.

Follow-up: What is the contract between hash and equality? If key_equal(a,b) is true, their hash values must be equal.

STLQ40

std::set vs std::unordered_set?

When do ordering and predictable complexity matter?

Show explanation & interview answer

std::set stores unique keys in sorted order, with logarithmic operations. std::unordered_set stores unique keys in a hash table, with average constant-time operations and linear worst-case behavior.

Interview answer: Choose set when sorted iteration, lower/upper bounds, or range queries are useful. Choose unordered_set when order is irrelevant and average hash lookup suits the workload.

STLQ41

How do you choose the right STL container?

Start from access patterns and invariants, not from a favorite container.

Show explanation & interview answer

Ask which operations dominate: indexed access, insertion/removal location, key lookup, ordering, duplicate handling, iterator stability, memory overhead, and cache locality.

  • vector: default sequence container, contiguous storage.
  • deque: efficient operations at both ends.
  • map/set: sorted keys and logarithmic operations.
  • unordered_map/unordered_set: average constant-time hash lookup.
  • list: specialized use cases requiring stable iterators and known-position insertion/erasure.

Follow-up: How do you validate a choice? Benchmark representative workloads and inspect memory behavior.

FundamentalsQ42

Process vs thread?

Compare memory isolation and resource sharing.

Show explanation & interview answer

A process is an execution environment with its own virtual address space and operating-system resources. Threads are execution paths within a process; they generally share process memory and resources but have their own stacks and execution state.

Trade-off: Threads make shared-memory communication efficient but require synchronization. Separate processes provide stronger isolation but communication usually requires IPC.

Follow-up: Do threads share local variables? Each thread has its own stack, but a pointer can refer to shared heap or global state.

ConcurrencyQ43

What is a mutex, and how does lock_guard use RAII?

Why is manual lock/unlock risky when exceptions or early returns occur?

Show explanation & interview answer

A mutex protects a critical section so only one thread at a time holds that lock. std::lock_guard locks the mutex on construction and unlocks it on destruction, including when control exits through an exception.

std::mutex m;
int count = 0;
void increment() {
    std::lock_guard lock(m);
    ++count;
}

Follow-up: Does this make every access to count safe? Only if all conflicting accesses follow a compatible synchronization strategy.

ConcurrencyQ44

std::lock_guard vs std::unique_lock?

When do you need a lock that can be unlocked and reacquired?

Show explanation & interview answer

lock_guard is a lightweight scope-bound lock for simple critical sections. unique_lock can defer locking, unlock and relock, transfer lock ownership, and work with condition variables.

Interview answer: Prefer lock_guard for simple locking and unique_lock when the extra control is required. Both support RAII.

Follow-up: What does a condition-variable wait do with a unique_lock? It atomically releases the lock while waiting and reacquires it before returning; always wait with a predicate to handle spurious wakeups.

ConcurrencyQ45

What is a deadlock, and how can you prevent it?

Explain the necessary conditions and practical prevention techniques.

Show explanation & interview answer

A deadlock is a situation where threads wait indefinitely for resources held by one another. The classic necessary conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait.

Prevention: use a consistent lock ordering, avoid holding locks unnecessarily, reduce nested locking, use std::scoped_lock for multiple mutexes, and consider timeouts or redesign when appropriate.

Follow-up: Is a race condition the same as a deadlock? No. A race is timing-dependent correctness; a deadlock is a progress failure due to waiting.

ConcurrencyQ46

What are atomic operations and memory ordering?

Why does atomicity alone not necessarily publish other data safely?

Show explanation & interview answer

std::atomic provides atomic operations on a particular object, avoiding data races on that object when used correctly. Memory ordering specifies how operations synchronize and how memory effects become visible between threads.

Common orders: relaxed provides atomicity without ordering other memory; release/acquire can publish data when paired correctly; seq_cst adds a single total order for sequentially consistent operations.

Interview answer: Start with mutexes unless atomics are justified. Choose the weakest ordering only when you can prove the required synchronization and visibility.

STLQ47

What is undefined behavior in C++?

Why can't you assume the program will behave consistently after UB?

Show explanation & interview answer

Undefined behavior means the C++ standard imposes no requirements on what the program does. Examples include signed integer overflow, out-of-bounds access, dereferencing a dangling pointer, and certain invalid lifetime operations.

Interview answer: The compiler may optimize under the assumption that undefined behavior does not occur, so results can differ across builds and optimization levels. Use bounds-safe APIs, sanitizers, and clear lifetime/overflow checks.

Follow-up: Is every unspecified behavior undefined? No. Unspecified behavior permits one of several valid outcomes; undefined behavior has no standard requirements.

Copy & MoveQ48

How do user-declared special member functions affect generated operations?

Why can adding a destructor change move behavior?

Show explanation & interview answer

C++ has special member functions such as default constructor, copy/move constructors, copy/move assignment operators, and destructor. Their implicit declaration or deletion depends on which members are declared and on the members/base classes' capabilities.

Interview answer: Do not memorize a simplistic rule that the compiler always generates all operations. Know the suppression rules—for example, a user-declared destructor suppresses implicit move-constructor and move-assignment declaration in the standard rules—and explicitly default/delete operations when appropriate.

Follow-up: What is = delete used for? It makes a function unavailable and produces a compile-time diagnostic when selected.

FundamentalsQ49

Predict constructor and destructor order in inheritance.

Explain the order before trying to guess printed output.

Show explanation & interview answer

Construction proceeds through virtual bases, direct bases, non-static data members in their declaration order, and then the constructor body. Destruction reverses the order: destructor body, members in reverse declaration order, bases in reverse construction order, with virtual bases destroyed by the most-derived object.

Interview answer: Member initialization follows declaration order, not the order written in the constructor's member-initializer list. Compiler warnings can catch mismatches.

Follow-up: Why is relying on initializer-list order dangerous? It can create subtle dependencies and warnings when the written order differs from actual initialization.

PolymorphismQ50

How do you solve constructor/destructor and virtual-function output questions?

Use a disciplined trace rather than guessing the output.

Show explanation & interview answer

Trace object lifetime in stages: identify static and dynamic types; list base/member construction order; determine which overload is selected; apply virtual-dispatch rules for the current construction/destruction phase; then reverse the lifetime sequence for destruction.

Interview answer: State which behavior is guaranteed by the C++ language and flag any undefined behavior instead of predicting a specific output. If code uses invalid lifetime, unsequenced side effects, or a non-virtual base destructor for polymorphic deletion, first determine whether the program is well-defined.

Practice: Write a tiny example, compile it with warnings enabled, then test with sanitizers where applicable.
